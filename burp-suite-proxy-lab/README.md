# Burp Suite Proxy Lab

## Objective

The objective of this laboratory is to configure Burp Suite as an interception proxy between two independent virtual machines.

The lab demonstrates how HTTP and HTTPS traffic can be routed through Burp Suite, inspected, recorded, and manually modified in a controlled environment.

## Laboratory Environment

- Hypervisor: Oracle VirtualBox
- Attacker machine: Kali Linux
- Target machine: Debian Linux
- Virtual network: NAT Network
- Network range: `10.10.10.0/24`
- Attacker IP: `10.10.10.3`
- Target IP: `10.10.10.4`
- Interception proxy: Burp Suite Community Edition
- Burp proxy listener: `10.10.10.3:8081`
- Browser: Mozilla Firefox

## Network Topology

```text
Target VM
10.10.10.4
Firefox
    |
    | HTTP / HTTPS
    v
Burp Suite Proxy
10.10.10.3:8081
Attacker VM
    |
    v
Destination Web Server
```

## Procedure

### 1. Virtual Network Configuration

Both virtual machines were connected to the same VirtualBox NAT Network using the `10.10.10.0/24` network range.

This allowed communication between the systems while keeping the laboratory environment separated from unrelated devices.

### 2. Connectivity Verification

The target machine verified connectivity with the attacker machine using ICMP.

The attacker machine was reachable at `10.10.10.3`.

### 3. Burp Suite Proxy Listener

A new Burp Suite proxy listener was configured on port `8081` and bound to all interfaces.

This allowed the target virtual machine to connect remotely to Burp Suite running on the attacker machine.

### 4. Firefox Proxy Configuration

Firefox on the target machine was configured to use `10.10.10.3` as the HTTP proxy on port `8081`.

The same proxy was configured for HTTPS traffic.

### 5. Burp Suite CA Certificate

The Burp Suite CA certificate was downloaded through the Burp Suite local web interface and imported into Firefox as a trusted certificate authority.

This allowed HTTPS traffic generated by the laboratory browser to be inspected through Burp Suite.

### 6. HTTP Traffic Inspection

HTTP requests generated from the target machine were routed through Burp Suite.

The requests could be inspected before being forwarded, including:

- HTTP method
- Host
- Request path
- Headers
- Parameters

### 7. HTTP History Analysis

Burp Suite HTTP History was used to review recorded proxy traffic.

Information available included:

- Request method
- Destination
- HTTP status code
- Content type
- Response size
- TLS information

### 8. HTTPS Traffic Inspection

After installing the Burp Suite CA certificate, HTTPS navigation from the target machine was successfully routed through the interception proxy.

This demonstrated how an authorized client can inspect its own encrypted web traffic through a trusted interception proxy.

### 9. Request Modification

An intercepted request was manually modified before being forwarded.

During the laboratory, the request path was modified to:

`GET /?lab=modified HTTP/2`

This demonstrates that client-generated requests cannot be considered inherently trustworthy by a web application.

## Security Analysis

The laboratory demonstrates an important web security principle: **the client is under the control of the user**.

A user can inspect and modify requests generated by their own browser before those requests reach the server.

Because of this, applications must not rely exclusively on client-side controls for security.

## Defensive Measures

Web applications should implement:

- Server-side input validation
- Server-side authorization checks
- Secure session management
- Secure cookie attributes
- HTTPS
- Appropriate logging and monitoring
- Minimal exposure of sensitive information
- Validation of every sensitive operation

## Conclusion

This laboratory established a complete interception environment using two separate virtual machines.

The target system generated HTTP and HTTPS traffic, while Burp Suite on the attacker/testing system operated as an interception proxy.

The exercise demonstrated proxy configuration, certificate installation, traffic inspection, HTTP history analysis, request modification, and the defensive implications of client-controlled web requests.
